## Accessibility declaration

ScrollSnooze is a self-directed digital wellbeing utility, not an accessibility tool for
people with disabilities. Do not claim `isAccessibilityTool=true`.

Explain these uses of Android AccessibilityService:

- Supported-app/foreground-window activity, window-change and scroll events, relevant visible
  text/descriptions, resource IDs, view classes, visibility and hierarchy identify players,
  detect item changes and ads, and count Instagram Reels/YouTube Shorts. Rules remain experimental.
- Salted item identifiers and dwell/transition checks prevent duplicate counts. The recent
  identifiers and detailed viewing-event records remain local during ordinary account backup.
- Service heartbeats, tracking status, supported-app and rule versions, and measurement-quality
  information describe availability, reliability and experimental/incomplete measurements.
- The signed-in backup includes daily tracking coverage with usage aggregates. Account allowance
  reconciliation sends cumulative per-app usage totals, not raw accessibility content.
- Meme breaks derive a temporary local script hint. Language-specific reaction/selection history,
  reaction IDs and caption indices persist locally for rotation and are not in normal account backup.
  The raw hint is not saved. Configured pauses use accessibility overlays;
  Android Back occurs only after the user taps Leave feed.
- Debug builds alone can create local text-free structure captures and diagnostic event exports;
  sharing requires explicit user action. These are not automatic diagnostic uploads.

Use the exact disclosure in `src/permissions/accessibilityDisclosure.ts`. Version 3 is checked
natively; prior acceptance does not authorize new tracking. Record a new video using the exact
submitted binary: opening app, full disclosure (slow scrolling), agreement, Android grant,
refusal and re-entry, and functioning counting. Demonstrate revocation as well.

## Data Safety: off-device transmission inventory

Google's Accessibility declaration covers access and local processing. Data Safety's collection
boundary is off-device transmission. Do not use the two questionnaires interchangeably.

| Off-device data | Proposed data type | Purpose and handling |
| --- | --- | --- |
| Daily `coverage` in POST `/v1/usage/sync` | App info and performance → Diagnostics | App functionality: indicate measurement completeness and gate trustworthy activity/score displays. Stored, not ephemeral. Linked to account and random device ID. |
| Backend request `route`, `status`, `ms`, `reqId`; unhandled error type | Diagnostics | Service operation and troubleshooting; app functionality and analytics where used to monitor service health. Generated by backend, rather than uploaded as an accessibility diagnostic report. Include when evaluating the complete Diagnostics answer; no raw body/header logging in the application logger. |
| `personalViews`, optional `personalAppViews`, eligible `views`, `adViews`, `minutes`; per-app account `views`/`usageMs` | App activity → App interactions (map to equivalent wording in the current Console) | Usage history, backup, account-wide limits, explicitly authorized aggregate-score features. Not ephemeral. |
| Random installation `deviceId` | Device or other IDs | Attribute and deduplicate per-device aggregates, synchronize account allowances and register notification delivery where configured. |
| Account ID, display name, authentication-derived profile | Personal info → User IDs / Name; assess Email address against the submitted release | Authentication and account management. These do not originate from accessibility nodes. Review the separate Google sign-in flow and identity-token handling. |

Ordinary daily upload fields are `localDate`, `tz`, `platform`, `deviceId`, `personalViews`,
optional `personalAppViews`, `views`, `adViews`, `minutes`, `coverage`, `rev`.
Account reconciliation adds incarnation, period/date/device IDs, revision/reset generation,
and cumulative per-app views/usageMs. These are existing APIs and remain unchanged.

For the confirmed daily-coverage flow, recommend **Diagnostics: collected, not ephemeral**.
Guest use is available; this particular upload is optional through the sign-in choice and
stops on sign-out. Do not finalize the overall optional/required answer until SDK collection
in the submitted release is checked: Google's rule applies to all users and sources.

AWS processes account data as the backend host. Evaluate the service-provider sharing exception
against the actual arrangements; do not mark all AWS hosting as independent third-party sharing.
Likewise, evaluate user-requested exports and expressly authorized score sharing under Google's
specific exceptions, rather than assuming every transfer is exempt. Do not claim diagnostics
are anonymous: daily coverage is associated with an account and device ID.

## Local-only material: do not declare it as uploaded

Raw accessibility text/captions, interface trees, salted fingerprints, detailed viewing events,
individual heartbeat rows, connection/event timestamps, language-specific meme selection history
and supported-app version lists are not
part of normal daily backup. Local processing still needs the in-app accessibility disclosure.
Do not add crash logs, battery, CPU, memory, frame-rate or other diagnostic collection that has
not been established. The current code does not upload an accessibility crash report.

## SDK verification and remaining release checks

The available debug dependency/manifest evidence includes Play Billing 8.0.0, Google Sign-In
(play-services-auth 21.4.0), Firebase Messaging 25.0.1 and Installations 18.0.0. Their presence
is not proof of accessibility-data transmission. No code path passing accessibility observations
to them was found. Messaging/Installations have their own documented technical metadata and
identifier practices. Optional delivery-metric/analytics behavior must be established from the
release configuration, not inferred from a Firebase measurement connector dependency.

Before submission, inspect the actual AAB's release dependencies, merged manifest and initialization;
verify SDK documentation for those versions; compare the current Console forms, privacy URL,
review video and deployed backend settings. Review billing/purchase-history and notification
collection separately if active; this scoped recommendation is not a complete pre-filled form
for every account/SDK feature. Android release-mode safeguards are unit-tested by clearing
FLAG_DEBUGGABLE; this is not equivalent to executing a signed release artifact on a device.

The website policy change must be deployed by the owner before relying on its public URL.
No deployment, Console submission or production AAB is performed by this change.

## Consent-cutoff clarification

V3 consent changes are serialized with accessibility work on Android's main thread. Withdrawal
stops scheduling and discards the active recorder/counter session without flushing dwell or time.
Valid-consent departures retain their original behavior. A minimal process-local service binding
reference and `lastConnectedMs` are available before consent for service-health reporting; these
are not window/content observations. No viewing observations, heartbeats or content-derived
traces are produced before consent. See ACCESSIBILITY_V3_CORRECTIONS.md for tests and limits.
